# LD LATTE — заявки на автоматизацию

Задача 3: небольшое приложение для личных заявок сотрудников. React + Vite обращается напрямую к Supabase Auth и PostgreSQL. Отдельного сервера нет.

[Открыть приложение](https://ld-latte-automation-requests.loosecedar1.chatgpt.site/) · [GitHub](https://github.com/redflag-ai/ld-latte-automation-requests)

## Возможности

- Регистрация, вход по email/паролю, выход и восстановление сессии.
- Создание, просмотр и редактирование своих заявок; смена статуса.
- Поиск по части названия и фильтр по статусу, в том числе одновременно.
- Состояния загрузки, сохранения, успеха и ошибки; блокировка повторной отправки.
- Адаптивные формы и список для телефона и компьютера.

## Настройка Supabase

Для текущего задания используется уже существующий проект LD LATTE: `fcrvsbdsofltyxrgocvs`. Новый проект создавать не требуется. Для повторного развёртывания в другой среде достаточно проекта Supabase с email Auth и приведённой миграции.

1. Откройте нужный проект в Supabase Dashboard, затем SQL Editor → New query.
2. Выполните содержимое `supabase/migrations/202611050001_requests.sql` один раз. Миграция создаёт новую таблицу и политики; существующие таблицы не удаляет. Если таблица requests уже существует, сначала проверьте её структуру: не удаляйте данные для повторного запуска.
3. В Authentication → Sign In / Providers проверьте, что разрешены email/password и регистрация новых пользователей. При включённом подтверждении email пользователь должен перейти по ссылке в письме перед входом. Для внешнего использования настройте SMTP по требованиям Supabase.
4. В настройках подключения/API скопируйте Project URL и **publishable key** (либо клиентский legacy anon key). `service_role` и secret key для приложения не подходят.
5. После выбора адреса приложения укажите его в Authentication → URL Configuration: Site URL и разрешённые Redirect URLs. Для локальной проверки добавьте `http://localhost:5173`.

## Запуск

Нужен Node.js 24 и pnpm 11.25.

```sh
pnpm install --frozen-lockfile
cp .env.example .env
```

Заполните в `.env` адрес Supabase и клиентский ключ. Затем:

```sh
pnpm dev
```

Откройте `http://localhost:5173`. Проверки и сборка:

```sh
pnpm test
pnpm build
pnpm preview
```

## Публикация

Приложение собирается в `dist`. Для статического хостинга укажите команду `pnpm build`, папку публикации `dist` и обе переменные из `.env.example` перед сборкой. После изменения переменных нужна новая сборка. Приложение использует один URL без клиентских маршрутов.

Текущая версия размещена на Sites. В `.openai/hosting.json` указан идентификатор существующего размещения. Для своего отдельного размещения используйте собственный хостинг и переменные окружения; копировать идентификатор Sites не нужно.

## Данные и защита

Таблица `public.requests` хранит id, user_id, title, description, category, status, created_at и updated_at. Категория и статус ограничены CHECK, пустые названия/описания запрещены. Новая запись получает статус «Новая» на уровне базы. Время изменения обновляет триггер.

RLS разрешает SELECT, INSERT и UPDATE только при `auth.uid() = user_id`. При INSERT дополнительно проверяется начальный статус. Клиент не может менять владельца, id и даты через UPDATE: выданы права только на редактируемые поля. Анонимный доступ и удаление через клиент не разрешены. Проверка работает и при прямом обращении к Supabase, независимо от интерфейса.

Клиентский ключ виден в сборке по назначению Supabase. Защита данных основана на авторизации и RLS. Реальные пароли, сессии, secret/service_role ключи и `.env` в репозиторий не входят.

Передача Save блокируется синхронным флагом до первого сетевого запроса, кнопка отключается до завершения. ID создаётся один раз на форму: повторная попытка с тем же ID не создаст вторую запись даже после неопределённого сетевого результата. При конфликте приложение предлагает обновить список и проверить сохранение.

## Проверка и сдача

- `docs/demo-checklist.md` — сценарии демонстрации и приёмки.
- `docs/ai-report.md` — использование AI и фактический статус проверки.
- `docs/known-limitations.md` — известные ограничения.
- `tests/model.test.js` — проверки поиска, фильтра и обязательных полей.
- `tests/rls.integration.js` — проверка изоляции двух пользователей обычным клиентом Supabase.
- `tests/rls-browser.html` — та же проверка через текущую сессию браузера, без передачи паролей тестовому скрипту. Доступна при `pnpm dev` по адресу `/tests/rls-browser.html`, в production-сборку не входит. Под аккаунтом A нажмите «Запомнить заявку A», затем войдите в основном приложении под B и нажмите «Проверить доступ B». После повторного входа A нажмите «Проверить сохранность A». Проверка оставляет одну тестовую заявку B.
- `tests/save-browser.html` — локальная проверка настоящей формы с контролируемой ошибкой сетевого адаптера: первый Save завершается ошибкой, повторный — успехом. Позволяет проверить блокировку двойного клика, сохранение введённого текста и восстановление кнопки. В Supabase данные не отправляет, в production-сборку не входит.

Интеграционную проверку запускают только в тестовом проекте с двумя зарегистрированными и подтверждёнными аккаунтами. Передайте переменные окружения `SUPABASE_URL`, `SUPABASE_PUBLISHABLE_KEY`, `TEST_A_EMAIL`, `TEST_A_PASSWORD`, `TEST_B_EMAIL`, `TEST_B_PASSWORD`, затем выполните `node tests/rls.integration.js`. Не сохраняйте пароли в коде или истории команд. Скрипт оставляет одну тестовую заявку для проверки; её ID выводится в результате. Удаление тестовых записей при необходимости выполняет владелец проекта отдельно.
